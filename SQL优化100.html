索引列上使用函数导致索引失效
电商订单查询 — 日期函数使索引无法命中
入门▶

📋 业务场景

某电商平台查询2024年1月的所有订单，订单表orders有500万数据，created_at字段建有普通索引。

🔴 问题SQL

SELECT * FROM orders WHERE YEAR(created_at) = 2024 AND MONTH(created_at) = 1;

🔍 发现过程

  • 运维反馈该查询慢，高峰期CPU飙高
  • EXPLAIN查看执行计划，type为ALL（全表扫描），key为NULL
  • 500万数据全表扫描，耗时3.2秒

💡 根因分析

对索引列使用YEAR()/MONTH()函数后，MySQL无法直接使用索引，因为索引存储的是原始值，不是函数计算后的值。

✅ 解决方法

方法1（推荐）：改写为范围查询

SELECT * FROM orders WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01';

方法2：使用函数索引（MySQL 8.0+）

CREATE INDEX idx_year_month ON orders ((YEAR(created_at)), (MONTH(created_at)));

📊 优化效果

  • type变为range，命中idx_created_at索引
  • 扫描行数从500万降至1.2万
  • 查询耗时从3.2秒降至12ms

LIKE左模糊导致索引失效
用户搜索 — 手机号尾号查询全表扫描
入门▶

📋 业务场景

CRM系统支持按手机号尾号查找用户，用户输入"*8888"查找尾号为8888的客户。

🔴 问题SQL

SELECT * FROM users WHERE phone LIKE '%8888';

🔍 发现过程

  • 客服反馈搜索功能卡顿，经常超时
  • EXPLAIN显示Extra为Using where，type=ALL
  • phone字段有索引，但LIKE以%开头无法使用索引

💡 根因分析

B+树索引按前缀有序存储，'%xxx'左模糊无法确定扫描起点，只能全表扫描。

✅ 解决方法

方法1：反向存储+前缀匹配（推荐）

ALTER TABLE users ADD phone_reverse VARCHAR(20); UPDATE users SET phone_reverse = REVERSE(phone); CREATE INDEX idx_phone_reverse ON users(phone_reverse); -- 查询改为 SELECT * FROM users WHERE phone_reverse LIKE REVERSE('8888') || '%';

方法2：使用Elasticsearch等搜索引擎

方法3：限制最小匹配长度+覆盖索引

SELECT * FROM users WHERE phone LIKE '138%8888';

📊 优化效果

  • 采用反向存储方案后，查询命中索引
  • 耗时从2.8秒降至15ms

隐式类型转换导致索引失效
会员查询 — 字符串ID传入数字
入门▶

📋 业务场景

会员表member_id为VARCHAR类型，Java代码中误用Long类型传入，导致隐式转换。

🔴 问题SQL

SELECT * FROM members WHERE member_id = '123456';

方法2：修改表字段类型（需谨慎评估）

ALTER TABLE members MODIFY member_id BIGINT;

📊 优化效果

  • 传入字符串后，type=ref，命中索引
  • 查询从1.5秒降至2ms

  • 耗时从200ms降至5ms

LIMIT深分页性能问题
订单列表 — 翻到10000页后系统卡顿
入门▶

📋 业务场景

订单管理系统，用户翻页查看历史订单，翻到第10000页时系统明显卡顿。

🔴 问题SQL

SELECT * FROM orders ORDER BY created_at DESC LIMIT 1000000, 20;

🔍 发现过程

  • 用户反馈翻页越往后越慢
  • EXPLAIN显示扫描行数=1000020
  • MySQL需要先扫描100万条记录，再返回20条

💡 根因分析

LIMIT offset, count 需要先扫描 offset+count 行，然后丢弃前offset行。offset越大，扫描量越大。

✅ 解决方法

方法1：基于主键/索引的游标分页（推荐）

SELECT * FROM orders WHERE (created_at, id) < ('2024-01-15 10:00:00', 12345) ORDER BY created_at DESC, id DESC LIMIT 20;

方法2：子查询减少回表

SELECT * FROM orders o JOIN (SELECT id FROM orders ORDER BY created_at DESC LIMIT 1000000, 20) tmp ON o.id = tmp.id;

方法3：限制最大页码

if (page > 500) { return "请缩小查询范围"; }

📊 优化效果

  • 游标分页扫描行数恒定为20
  • 查询从5.2秒降至8ms
